# 원료의약품 수급 매칭 플랫폼

제약사와 연구실은 원료가 언제 떨어질지 미리 알기 어렵고, 막상 부족해지면 그 원료를
당장 댈 수 있는 공장을 찾는 데 시간을 씁니다. 이 플랫폼은 그 두 가지를 한곳에서 해결합니다.
보유 재고가 임계치 아래로 내려가면 **미리 알려주고**, 그 물량을 실제로 공급할 수 있는
**GMP 인증 공장을 바로 찾아 조달**까지 이어집니다.

Spring Boot 3 기반 마이크로서비스 8개와 Vue 3 프론트엔드로 만들었습니다.
Eureka로 서비스를 찾고, Spring Cloud Gateway가 입구를 지키며, 인증은 OAuth2를 씁니다.
결제와 주문 확정은 Kafka 이벤트로 느슨하게 연결했고, 서비스마다 독립된 데이터베이스를 가집니다.

**발표자료는 [여기](Agile+MSA_조별발표_3반_2조.pdf)에 있습니다.**

---

## 시작하기 전에 — 이것만은 꼭 확인해 주세요

이 저장소를 클론하는 것만으로는 실행되지 않습니다. 딱 한 가지가 더 필요합니다.

전체 11개 컨테이너 중 **`auth-server`와 `api-gateway` 두 개는 강의에서 제공된 완성 이미지**입니다.
소스가 공개돼 있지 않아 저희가 빌드할 수 없고, Docker Hub에도 없습니다.
이미지 파일이 343MB~1.2GB나 되다 보니 GitHub 용량 제한에 걸려 저장소에 담지도 못했습니다.

그래서 **강의 자료로 배포된 이미지 tar 파일**이 필요합니다. 이미 갖고 계신 그 파일입니다.

| 파일 | 용량 | 어떤 환경에서 | 들어 있는 것 |
|---|---|---|---|
| `infra-images.tar` | 343MB | Intel Mac · Windows | auth-server, api-gateway |
| `msa-lecture-images-arm64.tar` | 1.2GB | Apple Silicon (M1 이상) | 위 두 개 + 나머지 전부 |

둘 중 환경에 맞는 하나만 있으면 됩니다. 나머지 9개 서비스는 이 저장소의 소스에서 직접 빌드되니
따로 준비하실 것이 없습니다.

준비물은 이 정도입니다.

- **Docker Desktop** — 컨테이너가 11개라 메모리를 8GB 이상 할당해 두시는 편이 안전합니다
- **Node.js 20 이상** — 프론트엔드 실행용
- 포트 `3000` `8080` `8081` `8083`~`8087` `8761` `9000` `3379` `9092`가 비어 있어야 합니다

## 실행하기

터미널에 그대로 붙여 넣으시면 됩니다.

```bash
# 1) 클론
git clone https://github.com/Jonny-rose-Kim/Agile-MSA.git
cd Agile-MSA/msa-MyService

# 2) 강의 이미지 tar를 지금 이 폴더(msa-MyService/)에 복사한 뒤 로드합니다
docker load -i msa-lecture-images-arm64.tar   # Apple Silicon
# docker load -i infra-images.tar             # Intel Mac · Windows

# 3) 백엔드 빌드 및 기동
docker compose up -d --build

# 4) 프론트엔드 (새 터미널을 열어서)
cd ../vue-frontend
npm install
npm run dev
```

3번은 처음 실행할 때 Gradle이 의존성을 내려받느라 **10분 넘게 걸릴 수 있습니다.**
로그가 멈춘 것처럼 보여도 기다려 주세요.

빌드가 끝나면 <http://localhost:8761>(Eureka)을 열어 보세요.
서비스 8개가 목록에 모두 올라오면 준비가 끝난 것입니다. 보통 1~2분 걸립니다.

> 서비스가 다 떠 있는데도 로그인이 잠깐 실패할 수 있습니다.
> Gateway가 Eureka에서 서비스 목록을 새로 받아오는 주기 때문인데, 1분쯤 지나면 정상화됩니다.

## 어떤 계정으로 로그인하나요

컨테이너를 띄우면 아래 두 계정이 자동으로 만들어집니다. 비밀번호는 둘 다 `password1234`입니다.

| 이메일 | 비밀번호 | 어떤 사용자 | 로그인하면 나오는 화면 |
|---|---|---|---|
| `student@lecture.com` | `password1234` | **제약사 · 연구실** (구매) | 원료 카탈로그 |
| `instructor@lecture.com` | `password1234` | **공급 공장** (판매) | 내 공급 품목 |

두 계정은 보이는 메뉴가 다릅니다. 구매자는 재고·주문·결제를, 공급자는 공급 품목과 수주를 봅니다.
회원가입도 동작하니 새 계정을 만들어 보셔도 됩니다.

로그인 버튼을 누르면 주소창이 `localhost:8080`으로 잠깐 바뀝니다. 오류가 아니라
**OAuth2 인증 서버를 거쳐 돌아오는 정상 동작**입니다.

## 5분이면 전체 기능을 볼 수 있습니다

`student@lecture.com`으로 로그인한 뒤 아래 순서대로 따라와 주세요.
데모용 원료 10건이 미리 들어 있어서 바로 시작하실 수 있습니다.

### ① 같은 원료를 어느 공장에서 받을지 고르기 &nbsp;·&nbsp; Ep-01 US1

`원료 카탈로그`에서 **세파졸린나트륨(`API-CEFA-500`)** 을 찾아 **상세**로 들어간 뒤,
아래쪽 **공급처 찾기**를 눌러 보세요.

같은 원료인데 두 공장의 조건이 다릅니다.

| 공장 | 단가 | 리드타임 | 인증 |
|---|---|---|---|
| 한국API공장 | 42,000원 | 14일 | GMP, DMF |
| 대한파마텍 | 39,500원 | 21일 | GMP |

싸지만 오래 걸리는 곳과, 비싸지만 빨리 오는 곳 중에 고르는 것 — 이게 이 서비스의 출발점입니다.

### ② 조달 신청하기 &nbsp;·&nbsp; Ep-01 US2

`조달 주문` 화면에는 값이 미리 채워져 있습니다. **조달 신청**만 눌러 주세요.

주문이 `PENDING` 상태로 생기고, `원료 카탈로그`로 돌아가 보면
**그 공장의 여유 생산능력이 주문한 수량만큼 줄어 있습니다.**
주문 서비스가 원료 서비스를 호출해 실제로 차감한 결과입니다.

### ③ 재고가 부족해지면 알아서 잡아내기 &nbsp;·&nbsp; Ep-02 US1

`재고 관리`에서 원료코드 `EXC-LAC-200`, 현재 재고량 `100`, 부족 임계치 `5000`으로 등록해 보세요.

임계치보다 재고가 적으니 곧바로 `부족`으로 표시됩니다.
`부족 알림`으로 넘어가면 심각도와 부족량까지 계산돼 있습니다.
백그라운드 스케줄러가 60초마다 다시 훑기 때문에, 재고를 채우면 알림에서 사라집니다.

### ④ 결제하면 주문이 확정되기 &nbsp;·&nbsp; Sprint 2

`결제 내역` 화면에는 결제 대기 중인 주문번호가 이미 들어가 있습니다. **결제하기**를 눌러 주세요.

그다음 `조달 주문`으로 돌아가면 **몇 초 뒤에** 주문이 `CONFIRMED`로 바뀝니다.
바로 안 바뀌는 게 정상입니다. 결제와 주문 확정을 직접 호출로 묶지 않고
**Kafka 이벤트로 연결**했기 때문입니다. 결제는 됐는데 주문 확정이 실패했다고 해서
결제를 되돌릴 수는 없으니, 둘을 떼어 놓고 각자 재시도하게 만들었습니다.

### ⑤ AI로 수요를 예측하고 공장을 추천받기 &nbsp;·&nbsp; Ep-03

`AI 추천`에서 **조회**를 눌러 주세요.

수요가 얼마나 늘었는지, 지금 속도면 재고가 언제 임계치를 밑돌고 언제 바닥나는지,
그래서 얼마를 발주해야 하는지, 그 물량을 댈 수 있는 GMP 공장은 어디인지가 한 번에 나옵니다.

> 이 화면은 **데모 데이터로 동작합니다**(화면 위에 안내가 떠 있습니다).
> 수요 예측의 근거가 될 발주 이력이 아직 실제 데이터가 아니라서 그렇습니다.
> `FORECASTER=llm`과 `OPENAI_API_KEY`를 넣으면 OpenAI 웹 검색 기반 예측으로 바뀝니다.

### ⑥ 공급 공장 입장에서도 보기 &nbsp;·&nbsp; Ep-02 US2

로그아웃하고 `instructor@lecture.com`으로 다시 들어와 보세요.

`내 공급 품목`에서는 여유 생산능력을 표에서 바로 고칠 수 있고,
`수주 관리`에서는 ②에서 넣었던 주문이 구매처 이름과 함께 보입니다.
권한이 분리돼 있어서 **다른 공장이 받은 주문은 보이지 않습니다.**

## 어떻게 만들어져 있나요

### 서비스 구성

| 서비스 | 포트 | 하는 일 | 데이터베이스 |
|---|---|---|---|
| api-gateway | 8080 | 모든 요청의 입구. JWT를 검증하고 `X-User-Id`를 심어 전달 | — |
| auth-server | 9000 | OAuth2 인가와 토큰 발급 | `lecture_db` |
| eureka-server | 8761 | 서비스 레지스트리 | — |
| user-service | 8081 | 회원과 권한 (구매자 / 공급자) | `lecture_db` |
| material-service | 8086 | 원료 카탈로그, 공급 가능 공장, 여유 생산능력 | `material_db` |
| order-service | 8087 | 조달 주문, 재고, 부족 감지, 수주 관리 | `order_db` |
| payment-service | 8084 | 조달 결제와 결제 완료 이벤트 발행 | `payment_db` |
| recommend-service | 8085 | 수요 예측, 소진 시뮬레이션, 공장 추천 (FastAPI) | — |
| vue-frontend | 3000 | 프론트엔드 | — |

프론트엔드는 **Gateway(8080)만** 호출합니다. 개별 서비스 포트를 직접 부르는 곳은 없습니다.

`enrollment-service`(8083)는 강의 템플릿에서 남은 서비스라 이 프로젝트 도메인과는 무관합니다.

### 서비스마다 데이터베이스를 나눈 이유

각 서비스가 자기 스키마만 소유하도록 `material_db`, `order_db`, `payment_db`로 나눴습니다.
컨테이너를 처음 띄울 때 `init-db/00_databases.sql`이 자동으로 만들어 줍니다.

다만 `lecture_db` 하나는 `user-service`와 `auth-server`가 함께 씁니다.
auth-server가 수정할 수 없는 완성 이미지라 같은 `users` 테이블을 봐야 하기 때문입니다.

### 결제가 주문을 확정하는 방식

```
POST /api/payments      payment-service  주문 금액 확인 → 승인 → 이벤트 발행
        ↓  order.payment.completed (Kafka)
order-service                            주문 PENDING → CONFIRMED
        ↓
주문 상세 화면                             폴링으로 상태 변화를 감지
```

## 잘 안 될 때

### 로그인을 눌렀는데 "페이지를 로드하지 못함"이 뜹니다

`auth-server`가 떠 있지 않아서입니다. 로그인은 브라우저를 `localhost:8080`으로 보내는
동작이라, 그 자리에 서버가 없으면 브라우저 단계에서 먼저 실패합니다.

```bash
docker compose ps                 # auth-server 가 Up 인지 확인
docker compose logs auth-server
```

강의 이미지 tar를 로드하지 않으셨다면 맨 위 안내를 다시 봐 주세요.

### 방금 띄웠는데 API가 503을 냅니다

Gateway가 아직 서비스 목록을 못 받아온 상태입니다. 1분쯤 기다리시면 됩니다.
<http://localhost:8761>에서 서비스 8개가 다 보이면 준비가 끝난 것입니다.

### 빌드 도중 `429 Too Many Requests`

Maven Central이 같은 공인 IP에서 오는 동시 빌드를 막은 것입니다.
Google 미러를 먼저 보도록 설정해 뒀지만 그래도 나면 잠시 후 다시 시도해 주세요.

`--no-cache`는 붙이지 마세요. 매번 전부 다시 받느라 오히려 더 잘 걸립니다.

### 포트가 이미 사용 중이라고 나옵니다

```bash
lsof -i :8080     # 누가 쓰고 있는지 확인
```

그 프로그램을 끄시거나, `docker-compose.override.yml`을 만들어 호스트 포트만 바꾸시면 됩니다.

### 처음부터 다시 하고 싶습니다

```bash
docker compose down -v        # 볼륨까지 지웁니다 (데이터 초기화)
docker compose up -d --build
```

데이터베이스와 시드 데이터가 자동으로 다시 만들어집니다.
